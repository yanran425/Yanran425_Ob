# Harness工程

## 1.Harness Engineering

### 1.1定义

- Harness=运行系统，它不是在教模型怎么回答，而是在设计模型怎么工作 （例如任务拆解、上下文管理、工具编排、权限设定、状态交接、验证、恢复、人类接管）。

- Harness Engineering正在重组Agent系统的构建与运维

### 1.2发展历史

- Prompt Engineering: 问什么
- Context Engineering: 让模型看到什么
- Harness Engineering: 整个系统如何运转

### 1.3核心原则

约束Agent的解决空间：反而提升表现。

> [!NOTE] 更少的工具=更少的步骤=更少的Token=更高的成功率。更多约束=更多自主性。

### 1.4核心模块

#### 1.4.1上下文工程

- 项目指令文件：AGENTS.md / CLAUDE.md——Agent启动时读取的知识基座。
- 动态上下文注入：从日志、指标、追踪信息中获取实时信息管道
- 上下文隔离：子Agent作为上下文防火墙，隔离窗口独立运行
- 上下文压缩：窗口填满时自动丢弃或摘要无关信息，对抗熵增

#### 1.4.2工具编排

- 精选工具集：工具不是越多越好——精心策划，移除冗余选项
- MCP协议集成：标准化工具接口——文件系统、API、外部服务统一协议
- 沙箱隔离：执行环境与生产系统隔离——如Stripe devbox模式

#### 1.4.3验证机制

- 确定性约束：Linter、结构测试、Pre-commit
- 生成评估分离：独立评估器，Anthropic模式
- 自动审查循环：多Agent审查迭代至满意

#### 1.4.4状态管理

- Session开始：无状态LLM
- 进度追踪：功能清单TODO
- Git检查点：增量提交/快照
- 检查点恢复：失败后从中断处继续

#### 1.4.5可观测性

- 执行追踪
- 质量分级
- 异常检测
- 反馈归因：失败模式追溯到Harness缺陷，驱动持续改进

#### 1.4.6人类接管

 - 关键节点必须让人类确认
 - 完整的Harness画像

## 2.Harness分析

## 2.1旧实践

- Test Hannes：软件测试基础设施
- CI/CD管道：持续集成与交付
- 任务编排：分布式工作流引擎
- 沙乡隔离：安全工程基础
- 可观测性：追踪、日志、指标

## 2.2新贡献

- 约束概率系统：约束对象从确定性代码变为概率推理
- 约束以提升；减少自由度反而提高可靠性
- 生成-评估分离；外部评估器优于自我批评
- 代码库即知识图谱：代码结构是Agent可推理性基础

## 2.3风险与局限

- 概念膨胀：精确性和使用性会被稀释
- 过度工程化：Harness必须是可撕裂的，过渡工程化在模型升级后会成为包袱
- 风险放大效应：多Agent会导致非预期解法发生率上升，提高意外污染概率

### 3.2 OpenAI

- 架构约束: 确定性自定义Linter和结构测试执行，不依赖Agent自觉
- 垃圾回收: 后台Agent定期扫描文档不一致与架构违规，对抗熵增

## 4.Harness设计重点

Harness的设计必须服务于具体场景目标。
- 企业场景更强调可靠，稳定、透明与可审计；
- 个人场景更强调简单、灵活与低门槛。

### 4.1面向企业的Harness

- 业务确定：目标、流程与边界更清晰
- 追求可靠：智能体输出要稳定、可复现
- 流程透明：关键步骤要可见、可解释
- 可审计追踪：日志、决策链路与结果可回溯
- 人可随时接管：支持人工介入、审核与兜底
- 有具体可度量指标：准确率、时延、成功率、成本等可评估

### 4.2面向个人的Harness

- 需求多变：问题类型丰富，场景不断变化
- 追求傻瓜式操作：尽量少配置，少学习成本
- 越简单越好：能一句话完成就不要多步操作
- 容错率高：允许试错、允许不完美，重点是好用
